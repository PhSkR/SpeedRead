###### 1.14.53

* Follow-up to 1.14.51 — the per-glyph "broken paragraph" symptom in Page View continuous mode kept reproducing on a real PDF after the NEL-only fix. Two additional changes land here, working together:
  - **`Char.isWordSeparator()` now also returns `true` for any `isISOControl()` char.** That covers every C0 control (U+0000 – U+001F + U+007F DEL) AND every C1 control (U+0080 – U+009F, which is where NEL at U+0085 lives). Previously only the single explicit NEL codepoint was recognised; the actual culprit on this user's document was a different control char in the same family. `isISOControl()` is a cheap range check (no per-char Unicode category lookup) so the broader recognition has no measurable cost. New regression tests cover U+007F DEL, U+0000 NUL, and U+0090 DCS as a representative C1 control.

###### 1.14.51

* Fixed Page View continuous mode rendering some passages as one-character-per-line with large vertical gaps (visible on first opening certain PDFs; the gap appeared to "go away" once TTS playback started, but only because the snippet overlay's opaque background covered the broken region). Root cause was in `TextProcessor.tokenizeWithBreaks` (`rsvp-engine`): the tokenizer's separator check called `Char.isWhitespace()`, which delegates to `Character.isWhitespace` and does NOT recognise U+0085 NEL — a UAX #14 mandatory line break — nor U+200B ZWSP / U+FEFF BOM. PDF text extractors occasionally interleave these characters between glyphs (PDFs with character-level positioning, multi-column layouts, or extracted footnote/sidebar text are common emitters); the tokenizer's `else` branch then appended the chars into the current word, producing one giant mega-token like `"in...tthese...`. The joined `cachedContinuousJoined` text passed to `continuousTextContent.setText(...)` carried those embedded NEL chars verbatim, and `TextView` (which line-wraps via ICU/HarfBuzz, both of which honour UAX #14) broke a line at every NEL — producing the visible per-glyph wrapping plus blank gaps wherever consecutive NEL runs occurred. Added a new internal extension `Char.isWordSeparator()` that returns `isWhitespace() || this == Char(0x0085) || this == Char(0x200B) || this == Char(0xFEFF)`, and replaced both call sites: `TextProcessor.tokenizeWithBreaks`'s separator branch and `DefaultRsvpEngine.rawTokenCount` (kept aligned so the engine's chunk-clamp / progress-percent math doesn't drift from the tokenizer's actual output). Codepoints written as `Char(0xXXXX)` rather than `'\uXXXX'` or raw glyphs so they stay greppable in source — every editor renders the underlying chars as zero-width / blank.
  - **Why NEL is treated as plain whitespace, not as a `LINE` / `PARAGRAPH` break**: a PDF that sprays NEL between every glyph would otherwise inject a `LINE_BREAK_PAUSE` per character into RSVP narration. Cleaning the token boundary is enough to fix the Page View rendering bug; pause-shape semantics stay opt-in to real `\n`. Same rationale for ZWSP and BOM (they're UAX #14 ZW class — break opportunity but not mandatory — and a no-break Glue char respectively, but neither is a meaningful pause point).
  - **Deliberately excluded** from the separator set: U+200C ZWNJ / U+200D ZWJ (legitimate within-word joiners in Arabic, Devanagari, etc.), U+200E LRM / U+200F RLM (BiDi marks, no break), U+00AD SOFT HYPHEN (typographer's hyphenation hint commonly embedded in justified PDF text). All four are documented in the helper's KDoc so future maintainers see the trade-off without re-deriving it.
  - **Bookmark-list cosmetic drift remains**: `BookmarkRepository.countWordsSample` still calls bare `isWhitespace()` for the bookmark preview's word count. Cross-module access to `isWordSeparator` would require widening the helper from `internal` to `public` on the engine surface; the bookmark count is metadata only (no functional impact on navigation, indexing, or playback) so the alignment is left as an explicit non-fix.
* Piper neural TTS now syncs the on-screen RSVP word to the actual audio playback frame instead of a uniform coroutine clock — the displayed word advances when `AudioTrack.playbackHeadPosition` crosses a per-word frame threshold weighted by syllable count (vowel-group heuristic with silent-`e` and `-le` corrections; char-length fallback for non-Latin scripts via `WordTimingPlanner`). Eliminates the cumulative drift between highlight and voice that made long Piper sentences finish their audio before the displayed word reached the period. Speech-rate setting propagates automatically because Piper's `OfflineTts.generate(speed=…)` already adjusts `samples.size` and the per-utterance frame thresholds derive from `samples.size`. New constants: `TTS_NEURAL_PLAYBACK_POLL_INTERVAL_MS`, `TTS_NEURAL_PLAYBACK_DRAIN_TIMEOUT_MS`, `TTS_NEURAL_MIN_WORD_WEIGHT`, `TTS_NEURAL_MAX_WORD_WEIGHT`, `TTS_NEURAL_NON_LATIN_CHAR_WEIGHT_SCALE`. New pure-Kotlin module-level helper `WordTimingPlanner` lives in `rsvp-engine` with a JUnit suite covering the syllable heuristic, weight bounds, and frame-threshold math. System TTS path is untouched (`UtteranceProgressListener.onRangeStart` already gives precise per-word timing there).

###### 1.14.10

* Fixed Listen (TTS) mode pauses still audible at 1.5x speech rate after the v1.14.6 chunker tuning. Root cause is the Android TextToSpeech *service-level* inter-utterance gap (~150-300 ms per `speak()` call) which has no API-level suppression — the gap exists regardless of `QUEUE_ADD`, lookahead depth, or chunk size. v1.14.6's strategy was to minimise *boundary frequency* (bigger chunks, deeper lookahead, soft-threshold sentence-flush at 60%), but the gaps that remained still landed in arbitrary spots and were perceptible at high rates. The unavoidable service gap then lands at exactly the spot where listeners expect a pause, and the voice's own natural sentence-end prosody (pitch drop, micro-pause) overlaps with it — combined silence reads as a single natural sentence-end pause rather than an abrupt mid-clause cut. `TtsChunker.chunk()` flush rule changes from `(sentenceEnd && sentenceSoftFull)` to plain `sentenceEnd`; the `sentenceFlushThreshold` parameter and `Constants.TTS_SENTENCE_FLUSH_THRESHOLD` constant are removed (vestigial). Paragraph still wins (preserves `hasParagraphBreakAtEnd`), word-cap still wins (run-on backstop on text without `.!?`), line-break-at-50%-full unchanged.
* Added a `NON_TERMINAL_ABBREVIATIONS` blacklist + single-letter-initial heuristic to `TtsChunker.endsSentence()` so the new every-sentence-flush rule doesn't re-introduce mid-sentence pauses at common abbreviations. Blacklist: `Mr.`, `Mrs.`, `Ms.`, `Dr.`, `Prof.`, `St.`, `Jr.`, `Sr.`, `vs.`, `etc.`, `i.e.`, `e.g.`, `cf.`, `a.m.`, `p.m.`, `A.M.`, `P.M.`, `Inc.`, `Ltd.`, `Co.`, `Corp.`, `Mt.`, `Ft.`, `No.`, `Vol.`, `Fig.`, `Ch.`, `pp.`, `p.`. Single-letter initials (`J.`, `K.`, `R.`) are caught by length: a token of the form `<single-uppercase-letter>.` is treated as non-terminal so "J. R. R. Tolkien wrote books." stays one utterance instead of fragmenting into four. Domain-specific abbreviations not in the list ("approx.", "Sgt.") still false-positive — cost is one mid-sentence pause per occurrence, no worse than the existing word-cap run-on fallback. Reference impl `app/libs/NeuralTtsEngine.piper.kt.reference` drops the threshold arg in lockstep.
